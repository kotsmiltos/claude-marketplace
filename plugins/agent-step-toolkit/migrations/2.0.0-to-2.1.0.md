# Migrate agent-step 2.0.0 → 2.1.0

> Severity: additive. Applied by `/pull-library`; readable standalone.

## What changed

**New module: the caller-digit capture primitives** (`capture.ts`, exported from `index.ts`).
Pure schema helpers for params that carry caller-dictated digits (a tax number, a card-number
tail). Nothing existing changes — no export is removed or reshaped, and runtime semantics are
untouched. The helpers:

- `digitsOnly(v)` / `digitsOnlyDeep(v)` — STT separator strip; the deep variant reaches into an
  array branch and collapses a SINGLETON array to its string (`["7070"]` ≡ `"7070"`), so the
  confirmation gate's parsed-params compare never reads a representation flip as drift.
- `callerDigits(shape, message)` — a digit-string schema whose shape rule is a REFINEMENT, never
  `.regex()` (a JSON-Schema `pattern` makes the model count digits itself and withhold or pad the
  call); `message` must stay COUNT-FREE (issue text rides `_debug` back to the model).
- `digitGroupsParam({ shape, message, describe })` — the "transcription field": the model passes
  spoken digit GROUPS as an array (or a single string); the JOIN happens in the preprocess, never
  in the model; the joined value validates against `shape`. Omission stays `undefined` (the
  carried/collected-value channel).
- `digitCandidatesParam({ shape, message, candidateMessage?, maxCandidates?, describe })` — the
  ambiguous-reading field: a single digit string or an array of every plausible reading for the
  EXECUTOR to try.

`describe` is REQUIRED on both builders and has no default: the library ships no model-facing
wording — field text is live prompt surface, owned and QA-gated per host. The authoring doctrine
and a proven description template are documented in `agent-step-api.md` `<caller_digit_capture>`.

## Why

Every voice host that captures caller-dictated digits has re-derived (or missed) the same three
rules, each learned from a live failure: a schema `pattern` produced withheld calls and padded
digits (the tool never ran, so no gate and no `invalid_params`); digit-count text in refinement
messages re-introduced the constraint through the `_debug` feedback path exactly when the model
was about to re-ask; and un-normalized representation flips between propose and execute burned
confirmation attempts on drift that wasn't. The mechanics are runner-contract consequences, so
they belong next to the runner. The WORDING deliberately does not: a shared default description
would let a future library bump silently change every host's live prompt surface, bypassing the
per-host live-run QA gates — hence the required `describe`.

The vendored `src/agent-step/*` is replaced wholesale by `/pull-library` (verbatim copy from the
toolkit; recursive — the tree gains top-level `capture.ts` + `capture.test.ts`). The suite grows
144 → 165. No project-side change is REQUIRED — existing hand-rolled digit params keep working.

## Manual follow-ups

1. **Hosts adopting the helpers on a confirm-gated field:** re-run the field's propose → execute
   sandbox tests and confirm a singleton-array re-call (`["7070"]` after `"7070"`) still EXECUTES
   rather than re-proposing — that equivalence is the singleton collapse working; if a host's old
   hand-rolled preprocess lacked it, this is a (desirable) behavior improvement worth one live QA
   pass on the affected flow.
2. **Do not centralize description text.** The temptation exists to share one `describe` string
   across hosts; the required-parameter design is deliberate — see Why. Copy the template from
   `agent-step-api.md` `<caller_digit_capture>` and adapt per host instead.
