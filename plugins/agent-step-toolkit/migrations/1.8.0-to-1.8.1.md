# Migrate agent-step 1.8.0 → 1.8.1

> Severity: internal (one behavior fix in the runner; no API change). Applied by `/pull-library`;
> readable standalone.

## What changed

**The auto-handoff error counter treats no-executor batches as NEUTRAL.** The reset now requires
that an executor actually ran in the batch: `errorCount` resets to 0 only when an EXECUTED batch
ends without a backend failure. Batches in which no executor ran — confirm-gate
proposals/re-proposals, prereq denials, param-validation failures, `abort_pending_input`, handoff
signals — neither increment nor reset the streak. The increment side is unchanged (a
backend-failure code implies an executor ran).

## Why

A confirm-gated action retried during a backend outage necessarily interleaves a proposal between
every two failing executes (the failed execute consumes the pending confirmation, so the retry
re-proposes). The proposal is a successful batch, so under the 1.8.0 rule it reset the counter —
fail → 1, re-propose → 0, fail → 1, … — making the auto-handoff threshold unreachable for EVERY
confirm-gated action: the deterministic escalation backstop silently degraded to "hope the caller
gives up". Executed work is the only proof the backend recovered; batches that never touch an
executor prove nothing and must be neutral. (Found by tracing a live simulated outage — the thread
checkpoint history showed the 1 → 0 oscillation.)

## Library replacement

`/pull-library` replaces `src/agent-step/*` wholesale (verbatim copy from the toolkit) — that
replacement is the whole upgrade. The suite grows 103 → 105 (two new error-counter neutrality
tests). No project-side API transforms.

## Manual follow-ups

1. **Re-check escalation tests for confirm-gated actions.** Hosts using confirm gates +
   `backendFailureCodes` now genuinely reach the threshold after N consecutive executed failures —
   a test that previously (wrongly) asserted the counter oscillates or the handoff never fires
   must now expect escalation.
2. **Don't rely on non-executed turns resetting the streak.** If any flow assumed an
   `invalid_params` / proposal / abort turn clears `errorCount`, it no longer does — only an
   executed batch without a backend failure resets it. This was never a documented behavior; if a
   flow needs a manual reset, clear the slot from a host hook instead.
