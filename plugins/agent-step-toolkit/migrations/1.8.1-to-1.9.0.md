# Migrate agent-step 1.8.1 → 1.9.0

> Severity: additive (one new export, one runner behaviour fix; no API removal, no signature change).
> Applied by `/pull-library`; readable standalone.
>
> **Scope warning — read before applying.** Unlike every prior migration, transforms 1–3 refactor the
> consumer's OWN architecture, and transform 3 edits the project's **graph module** (`src/agent.ts` /
> `src/graph.ts`) — outside `/pull-library`'s usual `src/agent-step/` + `src/tools/` target. They are
> behaviour-preserving by intent but not mechanical. Apply them under the skill's approval gate, one
> at a time, running the project's tests between each. A project may legitimately decline them and
> still take the library: transforms 1–3 are optional adoption, the library replacement is not.

## What changed

**1. `request_handoff` abandons transient runner state atomically.** The built-in action previously
wrote only the `handoff` slot:

```ts
// 1.8.1
const patch = { handoff: { reason: params.reason, context: params.context } } as Partial<T>;

// 1.9.0
const patch = {
  ...clearAllPatch<T>(),   // awaitingInput + currentFlow
  pagedRead: null,
  handoff: { reason: params.reason, context: params.context },
} as Partial<T>;
```

**2. New export `createTerminalHandoff(namespace, outcomes)`.** Builds a host's mapper from a
deterministic business outcome to a `{ reason, context }` pair, so the executor that established the
outcome can write the `handoff` slot itself:

```ts
import { createTerminalHandoff } from "../../../agent-step/index.js";

const terminalHandoff = createTerminalHandoff("lost_card", {
  identification_dead_end: "abandon",
  already_closed: "completed",
} as const);

// inside the executor
return {
  resultBody: { summary: M.already_closed, verdict: "already_closed" },
  stateUpdate: { lossReportOutcome: "already_closed", handoff: terminalHandoff("already_closed") },
  ok: true,
};
```

The outcome table is typed against `HandoffRequest["reason"]`, so the mapping is compile-time checked
and the returned `reason` stays literal per outcome.

## Why

A handoff abandons the active conversation path by definition. Leaving `awaitingInput`,
`currentFlow` and `pagedRead` behind meant a graph thread routed back later could resume work the
customer had already walked away from — worst case a pending confirmation, which locks every
following step until it resolves.

The export exists to delete a pattern that had independently appeared in several downstream agents:
an action writes an outcome enum, the model is then expected to issue a *second* `request_handoff`
call, it sometimes forgets, so the project adds a graph node (`force_escalate`, `force_complete`)
that watches the enum and forces the handback. That node duplicates knowledge the executor already
had at the moment it wrote the enum. Writing the slot there removes the gap the node was patching.

The downstream agent this was absorbed from went from **six graph nodes to three**: one was a true
forced-handoff node, replaced by executors writing the slot atomically; the other two were
model-input guards that did not belong in the graph at all (one was later deleted outright — see
the confirmation-nudge incident in `orchestration-boundaries.md`). Separately, it deleted three
wrapper actions with their executors, selectors, locale entries and test suites — that change alone
touched 22 files for +231 / −541 lines. Transforms 1 and 2 below are independent of each other;
transform 3 must come last, because the node can only be deleted once every outcome it watched is
covered by one of them.

The doctrine behind transforms 1–3, including the measured incidents, is
`skills/create-tool/references/orchestration-boundaries.md`.

## Library replacement

`/pull-library` replaces `src/agent-step/*` wholesale (verbatim copy from the toolkit). Files
changed: `runner.ts`, `handoff.ts`, `handoff.test.ts`, `index.ts`, `VERSION`. No files added or
removed. The suite grows 105 → 108.

## Manual follow-ups

1. **Transform 3 edits the graph module, outside `/pull-library`'s usual target.** Treat it as a
   separate reviewed change, not part of the mechanical pull. A project that takes only the library
   replacement plus transforms 4–5 is in a valid, supported state.

2. **Prompt sections that named a deleted action.** Transform 2 removes the action; the prompt block
   that taught the model to call it must be rewritten to the `request_handoff` pair in the same
   change, or the model will emit an unknown action. Re-run the prompt-input suite — this is exactly
   the layer that catches it.

3. **Choose each project's `{ reason, context }` vocabulary deliberately.** The context strings are
   part of the middleware-visible contract via `handoff_reason`. Reuse the former outcome name so
   logs and routing stay comparable across the change; if a downstream consumer matches on those
   strings, coordinate before renaming.

4. **A pending confirmation now clears on handoff.** If any flow relied on `awaitingInput` surviving
   a `request_handoff` (e.g. a host hook that re-read the pending action afterwards to compose a
   message), it no longer does. This was never documented behaviour, but check host code that reads
   `awaitingInput` in or after the handoff node.

5. **Routers and non-terminal agents.** A project with no terminal business outcomes and no forced-
   handoff nodes (an orchestrator/router, or a single-action utility agent) is unaffected by
   transforms 1–3; they should no-op. Confirm rather than assume, then take the library replacement
   and transforms 4–5 only.

6. **Do not use this migration as licence to add a confirmation nudge.** While simplifying a graph it
   is tempting to replace a deleted forcing node with a SystemMessage that tells the model to act on
   a pending gate. `orchestration-boundaries.md` § *Never add a graph-level "act now" confirmation
   nudge* documents why that is forbidden and what it cost.
