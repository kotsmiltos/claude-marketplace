# Migrate agent-step 2.4.0 → 2.5.0

> Severity: additive. Applied by `/pull-library`; readable standalone.

## What changed

Six additive capabilities, no removals and no signature changes. Every one is **opt-in** (or purely
additive result-surface visibility); a project that adopts none of them gets a byte-identical
model-facing surface after the copy. No new state slot — the internal-slot mask stays at eight keys.

- **`ConfirmationOpts.repeatReadBack?: boolean`** + the **`repeat_pending_confirmation`** control —
  the pending gate persists its exact `readBack` rendering (`awaitingInput.read_back`) and the
  sole-step control returns those stored bytes on a later caller turn: no re-render, no consent, no
  attempt spent. Repetition advances the gate's presentation-turn provenance, so repeat-then-execute
  cannot happen inside one caller turn.
- **`ConfirmationOpts.refuseProposal?(params, state)`** — propose-time, state-aware refusal with
  `invalid_params`-grade non-burning semantics (no gate stored, no attempt spent, no pending choice
  consumed).
- **`BuildAgentStepToolOptions.abortPolicy?: AbortPolicy`** — `requireActive` / `allowStandalone` /
  `allowedFollowers` / `allowedPendingTargets`; admission enforces abort-leads-the-batch with at most
  one declared domain follower. Omit → legacy permissive abort, byte-for-byte.
- **`HandoffSpec.modelRequestSchema?: z.ZodType<HandoffRequest>`** — narrow the model-facing
  `request_handoff` params (wire schema + runtime parse); the state slot and trusted effects keep
  the base schema.
- **`BoundedChoiceDef.renderRequest` / `renderResolution`** — engine-rendered choice offer/resume,
  riding control results as `read_back`.
- **Transcript visibility + one narrow admission relaxation** — the consuming step of a bounded
  choice is stamped `choice_consumed`; a batch may open with `resolve_bounded_choice` followed by
  that choice's own `directInputActions` (same-turn locks unchanged; nothing relaxed toward a
  mutation).

```ts
// Adoption sketch — each independently optional:
requiresConfirmation: {
  readBack: renderRecap,          // 2.3.0
  repeatReadBack: true,           // 2.5.0 — "pardon?" returns the stored bytes
  refuseProposal: (p, s) =>       // 2.5.0 — state-impossible proposal answered immediately
    hasCarried(s) ? undefined : { summary: msgs.nothing_carried, error: "nothing_carried" },
},
abortPolicy: { requireActive: true, allowedFollowers: ["select_entity"] },   // 2.5.0
handoff: { ...spec, modelRequestSchema: TerminalRoutesSchema },              // 2.5.0
boundedChoices: { resume_or_stop: { ...def, renderRequest, renderResolution } }, // 2.5.0
```

## Why

The same trajectory as 2.3.0 and 2.4.0 — mechanisms move into the engine — now centred on the
confirmation gate and on payloads that lived as prompt prose. A recap the model re-composes on a
"pardon?" turn is the same consent defect the 2.3.0 read-back closed, one turn later; a schema-valid
proposal over absent state stored a gate the caller was then asked to confirm; a permissive abort
let one utterance discard a pending gate and start new work; terminal routing pairs and the abort
contract drifted from admission because the prompt, not the configuration, stated them. Each
capability replaces a measured host workaround; misuse fails closed in every case.

## Library replacement

The vendored `src/agent-step/*` is replaced wholesale by `/pull-library` (verbatim copy from the
toolkit; recursive). **Two files are added**: `controls/repeat-confirmation.ts` and the top-level
`repeat-confirmation.test.ts`. For a project that does not opt in, the library replacement IS the
whole upgrade.

## Manual follow-ups

Adoption is opt-in per capability, and the prompt work is the larger half:

- **`repeatReadBack`**: enable per high-stakes confirm action that already has a `readBack`
  renderer. Teach the prompt: on the repeat control's success, speak the returned `read_back`
  verbatim; the gate is unchanged and the caller still owes the consent answer.
- **`refuseProposal`**: add where a proposal's validity depends on state (probe/consume patterns).
  Keep it a pure mirror of the executor's own consumption rule.
- **`abortPolicy`**: decide the narrowing deliberately — `requireActive` plus an explicit
  `allowedFollowers` list is the typical shape. The engine renders the configured contract into the
  abort description; remove any prompt prose that restates it.
- **`modelRequestSchema`**: move exact terminal reason/context pairs out of prompt prose into a
  typed union whose variants carry their own when-to-use descriptions; keep the prompt's
  terminal-classification section to intent rules only.
- **`renderRequest` / `renderResolution`**: adopt for choices whose offer/resume wording is fixed;
  pair with the prompt's single read-back authority (speak `read_back` verbatim when present).
- Re-pin prompt-input fixtures where behaviour intentionally changed (e.g. the leading-resolve
  batch now succeeds where it previously refused).
