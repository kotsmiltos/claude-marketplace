# Migrate agent-step 3.0.0 → 3.0.1

> Severity: internal. Applied by `/pull-library`; readable standalone.

## What changed

Three runner-internal behaviour fixes around the OTP and double-entry match gates. No export,
signature, type, or option changed — `index.ts` and `types.ts` are byte-identical to 3.0.0.

1. **Consumer-issuer fold allowed.** The match-then-OTP ordering guard
   (`otp_blocked_match_pending`) now exempts the pending match's own consumer. An action may
   declare both `requiresMatch` and `issuesOtp` — "confirming the value sends the code" — and is
   no longer refused while its own match gate pends:

   ```ts
   // action.ts — now a supported shape
   controller: {
     requiresFlow: "pin_setup",
     requiresMatch: { capturer: "propose_new_pin", maxAttempts: 3 },
     issuesOtp: { consumer_action: "confirm_otp" },
   }
   ```

2. **Consume-before-issue apply order.** On an ok verdict the runner now clears a consumed
   `requiresOtp`/`requiresMatch` gate BEFORE applying the `otp_issued` effect. `awaitingInput` is
   a single replace-on-write slot, so the old order (issue, then consume) had a consumer-issuer
   action wipe the OTP gate it had just opened. The two orders are equivalent when consuming and
   issuing are separate steps, so pre-3.0.1 tools are unaffected.

3. **OTP re-send admitted during the gate's own lockdown.** While an OTP gate pends, admission now
   also accepts a **same-flow issuer** of that gate as the batch's first step — an action whose
   `issuesOtp.consumer_action` is the gate's `for_action` AND whose `requiresFlow` equals the
   gate's `flow_ref`. A code that never arrived can be re-sent without `abort_pending_input`
   (which aborts the whole flow and everything captured in it). An issuer for the same consumer
   in a different flow is not a re-send and still refuses `otp_pending_locked`; note that a
   `startsFlow`-only issuer (no `requiresFlow`) is not admitted — give the re-sendable issuer a
   `requiresFlow` tying it to the gate's flow.

## Why

The folded consume-and-issue action is the natural shape for "the repeat entry is also the point
of no return" flows (set a secret, then a code confirms applying it): the guard's hazard — an
issuer overwriting a match whose consumer never ran — cannot arise when the issuer IS that
consumer. And a caller whose OTP never arrived previously had no path but abort, which threw away
the flow and forced them to start over; a re-send is now a first-class admitted step.

## Library replacement

The vendored `src/agent-step/*` is replaced wholesale by `/pull-library` (verbatim copy from the
toolkit). Changed files: `interaction/otp.ts`, `run/admission.ts`, `run/execution.ts`,
`runner.test.ts` (three new tests), `VERSION`.

This release is internal-only: **no `<transforms>` and no per-tool edits are needed** — the
library replacement alone is the upgrade.

## Manual follow-ups

- Prompt guidance that taught the model a workaround for a lost OTP ("first abort, then request a
  new code") can be simplified: re-calling the issuer while the gate pends now works directly,
  provided that issuer declares `requiresFlow` for the gate's flow.
- Tools that split "confirm the repeated value" and "send the code" into two actions purely to
  satisfy the old ordering guard may now fold them into one consumer-issuer action — a design
  choice, not a required change.
