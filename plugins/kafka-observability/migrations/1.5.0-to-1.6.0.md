# observability library 1.5.0 → 1.6.0

Privacy release: a **host-supplied content mask**. New module `content-mask.ts`
(+ `content-mask.test.ts`), re-exported from `index.ts`, and a new optional argument
`startup({ contentMask })`. The library applies the policy at its single emit funnel, to
the content fields of every event — `inputs`, `outputs`, `error`, and each
`events[].kwargs` — leaving trace identity, the timeline, `metadata`, `serialized`, the
envelope `thread_id` and all JSON numbers untouched.

The policy itself stays with the application on purpose. The library redacts credentials,
which look the same everywhere; domain PII does not — whether a nine-digit run is a tax id
to hide or an order reference to keep, and whether a card number should vanish or keep its
last four, are facts about the project's flow. The same division `traceBackendCall`'s
security contract has drawn since 1.5.0, now available for every run rather than just
backend calls.

Additive only: no export removed or changed, no env key added (masking is code, because a
policy is a function), event schema untouched. **With no policy wired, emitted bytes are
identical to 1.5.0** — guarded by a regression test on the omitted-argument payload.

One behaviour change worth knowing even if you wire nothing: `events[].name` and
`events[].time` are excluded from the masked scope. The library builds that array itself
(`sanitizeRunEvents` → `{name, time, kwargs}`), so they are machine-generated timeline
data; without the carve-out a digit policy rewrote every streaming-token timestamp to
`##:##:##`.

<transforms>

**1. No mandatory transforms.** Library file replacement only — the wholesale vendored copy
brings both new files and the `index.ts` re-exports.
check: `grep -q "content-mask" src/observability/index.ts` after vendoring.

**2. Optional — wire a masking policy.** Nothing is masked until you do. Decide with the
user; declining is a valid answer that preserves 1.5.0 behaviour exactly.

First look for a policy the project already owns, rather than writing one:

```bash
ls src/**/redact*.ts src/**/*redaction*.ts 2>/dev/null
grep -rln "mask\|redact" src --include='*.ts' | grep -v src/observability
```

**2a. A domain masker exists.** Compose it — digit pass INSIDE, key tiers OUTSIDE. Order is
load-bearing: key-based tiers trim a TAIL (`***4410`, `***567`) and the digit pass
preserves tails, so the tiers still land on the real last digits. Reversed, the tiers' own
`***4410` is re-masked to `***####` and the last-four the flow itself reads back is gone.

```ts
// graph entry module (the one that already calls startupObservability)
import {
  startup as startupObservability,
  mapStringsDeep,
  maskDigitsInText,
} from "./observability/index.js";
import { redactValue } from "./tools/<tool>/backend/redact.js";

startupObservability({
  contentMask: (value) => redactValue(mapStringsDeep(value, maskDigitsInText, { keys: true })),
});
```

`keys: true` is not optional decoration: a state slot keyed BY the sensitive value — the
card-flow agents keep `verifiedCards` keyed by full PAN — is unreachable by any key-*name*
policy, which reads keys and masks values.

Audit the reused masker for two things before proposing it, and tell the user what you
found:

- **A bare `name` key.** Inside run content that also matches LangChain's own
  (`ToolMessage.name`, `tool_calls[].name`), so "which tool the model called" is masked
  inside `outputs`. The run's own `data.name` is out of scope and survives, so node/tool
  analytics are unaffected. Usually acceptable — but say so rather than letting it surprise
  someone reading a trace later.
- **Whole-string digit rules.** A masker written for backend JSON may strip non-digits from
  an entire string and mask it if the total reaches a threshold. On model prose that
  collapses the whole utterance to `***1234`. Use the project's free-text sibling (or this
  library's `maskDigitsInText`) for strings, and keep the key rules for structure.

**2b. No masker exists.** Offer `digitContentMask()` and name its rule out loud: runs of 7+
digits become `***<last4>`, shorter runs (PINs, OTPs, amounts) are masked digit-for-digit,
so four real digits of every long identifier still reach the topic. `keepLast: 0` removes
even those.

```ts
import { startup as startupObservability, digitContentMask } from "./observability/index.js";

startupObservability({ contentMask: digitContentMask({ keys: true }) });
```

**3. Verify.** `npx tsc --noEmit`, then `npm run test:observability` (158 tests). Confirm
the startup line reports the state you expect:

```
[observability] Kafka run tracing initialized (...) content_mask=host
```

`content_mask=off` means no policy is installed — correct if that was the decision, a bug
if it wasn't.

**4. Deployment.** Nothing to add: no env key, no secret, no Key Vault reference. The
policy travels in the code.

## Scope, so nobody has to read the source to find out

| Masked (when a policy is wired) | Never masked |
|---|---|
| `inputs` | `run_id`, `trace_id`, `parent_run_id`, `dotted_order` |
| `outputs` | `start_time`, `end_time`, `latency_ms` |
| `error` | `events[].name`, `events[].time` |
| `events[].kwargs` | `metadata`, `serialized`, `tags`, `name`, `run_type` |
| | envelope `thread_id` (never part of `data`) |
| | every JSON number (token/usage counters) |

Limits that no digit policy can fix, and that the user should hear before they assume the
topic is clean: numbers spoken as **words** ("five zero five zero") are not numerals;
non-numeric PII (names, addresses, free-text answers) needs key rules, not digit rules;
and `metadata` is out of scope, so PII must not be passed through `configurable`.
